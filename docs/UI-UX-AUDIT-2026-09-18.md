## 0. 结论摘要

**这是一个工程质量明显高于同类个人项目的界面。** 它最难得的地方是：**每个设计决策都留了实测依据**——`styles.ts` 里成段写着"实测 2.28:1""实测恰好 4.4996:1，比 AA 的 4.5 差一点点""实测 38 vs 36"。

本轮审核最重要的结论有两条：

**① 深色主题是干净的。** 10 屏、两套主题各全量扫过一遍对比度：**深色主题 0 处不达标**。我一度以为深色的语义混色配方写反了（原因见 §1.3），最终用"逐元素自身背景 + 祖先逐层合成"的正确算法 + 解析器自检推翻了它——`color-mix(in srgb, 语义色 55%, label-primary)` 这个配方在两套主题下都成立（深色下 `label-primary` 变浅，混出浅底，而 `label-primary-foreground` 同步变深，仍然互补）。

**② 问题全部集中在浅色主题的 4 个色值上。** 深色下它们全部达标，浅色下不达标——这与"团队在深色主题下逐项调过、浅色下漏了"的痕迹完全吻合。

| 类别 | 数量 | 最严重的一条 |
|---|---|---|
| 浅色主题对比度未达 AA | **4 个色值，共 33 处实例** | `.jh-chip-warn` 白字配 `#f59e0b` ＝ **2.15:1** |
| 表单控件缺可感知标签 | **9 个控件** | 面试「时间 / 形式 / 通勤」三个必填控件 |
| 状态语义缺失（ARIA） | 3 项 | 标签栏无 `aria-current`；实时状态非 live region |
| landmark 冗余 | 流水线 7 个 + 简历中心 1 个 | 看板列头 `<header>` 落在 `<section>` 内 |

**没有发现任何阻断性问题**：10 屏全部可切换、键盘全通、320–1440px 无横向溢出、控制台 0 错误、0 失败请求、0 个无名控件（除下列 9 个表单控件）。

**十条最重要的问题**：

1. **浅色：`.jh-chip-warn` 2.15:1**（看板样本量提示、简历体检告警）—— 同一个文件第 40–57 行专门解释过"语义色当底色配白字只有 2.0–2.3:1"，却在这一处又落回同一个坑。
2. **浅色：`.jh-salary` 4.23:1 × 20 处**（岗位库薪资）—— 决策第一眼要看的信息，差 0.27。
3. **浅色：`.jh-btn-info` 4.23:1 × 10 处**（导出 PDF / 导出 Word）。
4. **浅色：`.jh-board-age` 3.71:1**（"卡了 N 天"）—— 这正是流水线屏要回答的问题。
5. **9 个表单控件没有可感知标签**：面试（3）、简历中心（4）、校招（2），多数只靠 placeholder。
6. **标签导航无 `aria-label`，当前标签无 `aria-current`** —— "我在哪一屏"对读屏不可达。
7. **`.jh-live`「实时已连接」不是 live region**，且全项目 `aria-live` 计数为 0。
8. **流水线一屏产生 8 个 `banner` landmark**（`.jh-board-col` 是 `<section>`，内套 `<header>`）。
9. **岗位库首屏 607px（54% 屏宽）用于一段空态灰字**。
10. **消息列表没有"已回复"标记**，流水线与面试的终态动作（已拒绝/已取消）与推进动作视觉权重完全相同。

### 2.1 对比度

#### A-1 [major] 浅色主题：`.jh-chip-warn` 白字配橙底 ＝ 2.15:1 【实测】

- **位置**：`styles.ts:429-430`
  ```css
  .jh-chip-warn{background:var(--dsw-alias-state-warn-primary);
    color:var(--dsw-alias-label-primary-foreground);font-weight:600;cursor:help}
  ```
- **实测**：浅色 `rgb(255,255,255)` on `rgb(245,158,11)`，11px/600 → **2.15:1**（需 4.5:1）；实例 **11 处**（看板「⚠ 样本 2 条 · 悬停看口径」×1、简历中心「⚠ 体检 N 项」×10）
- **深色对照**：`label-primary-foreground` 变 `#0f1115` → 近黑字配橙底 ＝ **8.80:1 达标**
- **为什么这条最该修**：同一个文件 `:40-57` 有整段说明——"主题里的 `state-*-primary` 是**指示色**，不是文字色：拿来当文字色在 `bg-base` 上只有 2.0–2.3:1（成功 #22c55e 2.28、警告 #f59e0b 2.15）"。**2.15 这个数字在本文件里已经被写下来过一次**，而这里正是把 `#f59e0b` 当**底色**配白字，落回同一个数值。
- **建议**：底色改用 `--jh-warn-fg`（`.jh-todo-warn` 已在用的配方），实测浅色 **5.57:1**、深色 **12.08:1**，两套主题都达标；或改深色文字配浅橙底。
- **事实 vs 判断**：比值与实例数是实测；"该修"的优先级是判断。

#### A-2 [major] 浅色主题：`.jh-salary` 4.23:1（决策关键信息） 【实测】

- **位置**：`styles.ts:189` `.jh-salary{font-size:15px;font-weight:700;color:var(--dsw-alias-state-business-primary)}`
- **实测**：浅色 `rgb(65,118,230)` on `#fff`，15px/700 → **4.23:1**（需 4.5:1）；实例 **20 处**（岗位库当前页每张卡）
- **为什么 4.5 而不是 3**：WCAG 的"大文本"门槛是 ≥24px，或 ≥18.66px 且 ≥700。15px/700 **不够大**，所以按正文要求 4.5:1。
- **深色对照**：`--dsw-alias-state-business-primary` 在深色下是 `#679efe` → on `#232324` ＝ **5.91:1 达标**
- **建议**：沿用本文件已有的做法——`color-mix(in srgb, var(--dsw-alias-state-business-primary) 55%, var(--dsw-alias-label-primary))`，或直接把 `#4176e6` 调深一档。
- **影响**：薪资是用户扫岗位列表时第一眼要找的信息；本屏 20 处实例让这个色值成为**出现频率最高的不达标项**。

#### A-3 [major] 浅色主题：`.jh-btn-info` 4.23:1 【实测】

- **位置**：`styles.ts:529-531`
  ```css
  .jh-btn-info{border-color:transparent;font-weight:600;
  ```

- **实测**：浅色 `#fff` on `rgb(65,118,230)`，13px/600 → **4.23:1**；实例 **10 处**（简历中心「导出 PDF」「导出 Word」）

- **注意这是单点遗漏而非系统性缺陷**：同一文件里 `.jh-btn-primary`（近黑 + 白）＝ 18.90:1、`.jh-btn-danger`（浅色混色红 + 白）＝ 9.75:1，都达标。只有 info 蓝这一档没走混色。

#### A-4 [major] 浅色主题：`.jh-board-age` 3.71:1 【实测】

### 2.2 语义与可访问性

#### B-1 [major] 9 个表单控件没有可感知标签 —— 多数只有 placeholder 【实测】

| 屏幕 | 控件 | 实际可用的标签 | 视觉标签是否存在 |
|---|---|---|---|
| 消息 | `textarea.jh-textarea` | 无，只有 `placeholder="把 HR 发来的消息贴在这里…"` | 无 |
| 面试 | `input[type=datetime-local].jh-input` | 无 | 无 |
| 面试 | `select.jh-select`（现场/视频/电话/其它） | 无 | 无 |
| 面试 | `input[type=number].jh-input-narrow`（通勤分钟） | 无 | 无 |
| 校招 | `input[type=text].jh-input` | 无 | 无 |
| 校招 | `input[type=date].jh-input` | 无 | 无 |
| 简历中心 | `textarea.jh-textarea`（个人简介） | 无 | **有**（`<h3>个人简介</h3>`，但未关联） |
| 简历中心 | `input.jh-chip-input`（技能输入） | 无 | **有** |
| 简历中心 | `input.jh-chip-input`（标签输入） | 无 | **有** |

- **对比**：岗位库、看板、采集的筛选控件**都有** `.jh-field > span` 视觉标签，可访问性良好。说明项目有能力做对——这几处是漏了。
- **判断**：placeholder-as-label 有两个后果：输入后标签消失；读屏只念占位文本，部分读屏器不把 placeholder 当名称。面试那三个控件影响最大——**用户必须填对时间与形式才能录入，而读屏用户不知道哪个框是什么。**
- **补充 [minor]**：`.jh-field > span` 这类**视觉标签本身也没和控件关联**（无 `for` / `aria-labelledby`），所以严格说"看得见标签"的字段在 DOM 层同样缺名称，只是比纯 placeholder 略好。建议统一改成真 `<label for>`。

#### B-2 [minor] 标签导航无 `aria-label`，当前标签无 `aria-current` 【实测】

- **位置**：`panel.tsx:115-131`
- **实测**：`nav.jh-tabs` → `aria-label: null`；`.jh-tab-active` → `aria-current: null`、`aria-selected: null`、`role: null`
- **影响**：读屏用户听到 10 个按钮，**不知道当前在哪一屏**——"当前"只由 CSS 类表达。

### 强烈建议：把对比度做成 CI 断言（这是本轮最重要的流程建议）

项目有 485 个单测，但**没有任何对比度 / 焦点 / 键盘 / landmark 的自动化断言**。本轮的 A-1–A-4（4 个色值、33 处实例）**全部是浅色主题下的静态色值问题**——它们是可被一行测试抓住的，却一路进了主干；而深色主题因为被逐项调过，0 失败。

建议把这轮脚本里的探针收敛成 `test/ui/a11y.test.ts`（用仓库已有的 jsdom 或 headless 路径），断言：

1. **对比度**：本报告用的算法（元素自身背景 + 祖先逐层合成、正确解析 `#rgb` / `#rrggbbaa` / `rgba()` / `color(srgb …)` / `color(srgb … / a)`），**浅色与深色各跑一遍**，要求 0 失败。

## 8. 第三轮：流水线屏（站在用户角度的重做，2026-09-18）

§0–§7 修的是**可达性**（"读不读得清"）。这一轮修的是**可用性**：
用户拿着自己的数据打开「流水线」，能不能一眼看懂、能不能顺手操作。

### 8.1 先量，再改

| 实测项（1440px 视口） | 改前 | 改后 |
|---|---|---|
| 看板容器 / 内容宽 | 1000px / **1656px** | 1000px / **1000px** |
| 横向溢出 | **656px**（必须滚动） | **0** |
| 有内容的列宽 | 228px（被 6 个空列平分） | **398px** |
| 空列宽 | 228px（占满一个盒子） | **66px**（折叠成一行胶囊） |
| 768px 窄面板下溢出 | **980px** | **0** |
| 能否一眼看完全流程 | 否（1656px 里只看得到前 4 列） | **是**（"全流程"一条读完 7 个阶段） |

**为什么原来会溢出**：列是 `flex:0 0 210px`（连 padding 实际 228px），
`7 × 228 + 6 × 10 = 1656px`，而 `.jh-screen` 的 `max-width` 是 1000px ——
**与视口无关，宽屏也照样溢出**。溢出 656px 而全屏内容只有 114px（一张卡）：
在途阶段只有一个位置时，7 个固定宽列纯粹是浪费。

| # | 问题（用户角度） | 改法 |

## 10. 第五轮：采集浏览器「空闲自关」（NFR-7 / C12，2026-09-18）

### 10.1 起因：一个被问出来的不一致

有人问"采集完应该关闭浏览器，这个实现了吗"。核代码后的答案是**没有**，
而且这是当前实现里**有意**的：`browser.ts` 的上下文是全程常驻的进程内单例，
`close()` 只在**插件卸载**时被调用（`runtime.ts`），`release()` 还明确
"只剩一页时留着，别把用户的窗口关掉"。两条回收路径只有：用户手动关窗、插件卸载。

但同一项目里 **PDF 渲染器是有空闲自关的**（`render/pdf.ts`：懒启动 + 空闲 90 秒关闭，
注释写着"不留孤儿进程（C12）"）。`ARCHITECTURE.md` 的 **NFR-7** 也明确要求
"单轮资源可控：浏览器句柄关闭、无泄漏"。所以这是**同一个目标在两处做法不一致**。

### 10.2 做了什么

给采集浏览器加**空闲自关**，时长可在设置里改：

| 项 | 值 |
|---|---|
| 默认 | **10 分钟** |
| 可选范围 | 0–240 分钟；**0 = 不自动关闭**（保留旧行为） |
| 设置路径 | 设置页 →「浏览器」→ 采集浏览器空闲多久后自动关闭 |
| 生效 | 改完**立刻**作用到浏览器实例（不用重启插件） |
| 存储 | `setting` 表 `key='browserIdleCloseMinutes'`、`scope='global'` |

**为什么默认 10 分钟而不是 PDF 那样的 90 秒**：抓取浏览器是 headful 的，启动要几秒
还要复用登录态；连续补跑 / 手动连点两次采集很常见，90 秒会让第二次采集每次都冷启动。
10 分钟既盖住"连着跑几次"，又不至于让一个 Chromium 整晚挂在内存里。

### 10.3 三条守卫（否则会关掉用户正在用的窗口）

到点时**再问一次**"现在能关吗"，只有明确返回 `false` 才拦住：

1. **登录引导轮询中** → 不关。那个窗口正是用户**正在输密码**的地方
   （`LoginFlow.isRunning()`，为本轮新增）。
2. **采集 / 补跑进行中** → 不关（`mutex.isBusy()`）。
3. 被拦住之后**重新计时**，而不是放弃 —— 否则一次登录引导就永久取消了自关。

另外两处时序不变量，都写进了注释与测试：
- **任何"开始干活"都先取消已排的关闭**（`ensure()` 开头 `clearIdle()`），
  否则会出现"新一轮刚开跑，上一轮排的定时器到点把它关了"；
- **重排之前先撤旧的**，否则同一时刻会有两个定时器、早的那个先到点。

### 10.4 落地位置（为什么这样切）

| 文件 | 职责 |
|---|---|
| `src/host/platform/idle-close.ts` | **新增**。纯时序逻辑（取消 / 到点复问 / 重新计时 / 改时长），注入 `TimerPort` 与 `close` 回调 —— 因此**不必真等 10 分钟、也不必真起浏览器**就能测 |
| `src/host/platform/browser.ts` | 接上 `createIdleCloser`；`release()` 末尾起表（所有采集与登录路径的唯一入口），`ensure()` 开头取消 |
| `src/host/browser-config.ts` | **新增**。设置键的读写 + `normalizeBrowserConfig` 收敛（NaN/负数/越界） |
| `src/host/settings.ts` | snapshot 加 `browser` 段；patch 支持 `browser`；**不走 guard 令牌**（它是资源设置，不是闸门） |
| `src/host/http/router.ts` | `settingsPatchOf` 白名单加 `browser.idleCloseMinutes` |
| `src/client/screens/settings.tsx` | 「浏览器」卡片：数字输入 + 问号说明 + 当前状态说明 |
| `src/client/field-hint.tsx` | **新增**。`FieldHint` 原本是 `collect.tsx` 的私有组件，设置页也要用 → 抽出来共用，不复制 |

**为什么不塞进 `GuardConfig`**：那一层是安全闸门（额度、冷却、审批），
其键模型一律不能改（`MODEL_FORBIDDEN_KEYS`）。"浏览器空闲多久关"是资源/体验设置，
混进去会让"模型能不能改"变得含糊。所以单独一个键，并加入 `MODEL_EDITABLE_KEYS`。

### 10.5 测试（新增 12 条，总计 497 → 全绿）

`test/platform/idle-close.test.ts` —— 用项目已有的 `createManualTimer` 手动推进时间：

- 到点关闭；差 1ms 不关；关完不再排
- **重排先撤旧的**（否则旧的定时器会把新一轮关掉）
- 到点被守卫拦住 → **不关且重新计时**，忙完之后到点照关
- 守卫不传 / 返回 true → 默认关门（不是默认留着）
- 时长设 0 → 撤销已排的那次、之后不再关
- 运行期改小时长 → 立刻按新值到点
- 取消后不再触发，且**不留幽灵定时器**（`pending() === 0`）

`test/host/browser-config.test.ts` —— 坏输入收敛与落库：
非数字/NaN/Infinity 退回默认、负数按 0、越界收到上限、小数四舍五入、
0 能存住、键名与 scope 与 shared 常量一致。

### 10.7 刻意没做

- **没把默认值设成"关"**：那等于没加这个功能；也没设成 90 秒（会让连续采集每次冷启动）。
- **没做成"每次采集完立刻关"**：那会牺牲复用，而且用户看采集过程的窗口会闪一下就没。
  空闲 10 分钟是"用完了自己走"，不是"用完立刻走"。
- **没动 PDF 渲染器的 90 秒**：它是一次性无状态渲染，与抓取浏览器的复用需求不同。
